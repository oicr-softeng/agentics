# Checking for upstream updates

Whether this project's agentics integration is behind the upstream template, and what to do about it. Split out of `convention-levels.md` because it is read on a different trigger than the rest of that file: session start under the gating below, rather than when someone is deciding where a new convention belongs. A session that never stopped skips it at a repeated session-start signal, as ceremony, per `session-discipline.md` § Session-start signals; a restart or context loss runs it again.

Related but distinct: this file decides *whether* there is drift and classifies what changed. `upgrading-adoption.md` is the procedure for reconciling a project once drift is found, and this file hands off to it.

**One part is not gated by anything the user opted into:** § Security notices for every pinned project runs at session start in every pinned project. Everything else here is the full check, under the gating that follows.

Propagation isn't only outbound. A project's pin falls *behind* agentics as releases are published, by design, and the user's global copies of `AGENTS.softeng.md`/`AGENTS.overture.md` drift behind as the template evolves after they were copied. Two separate questions decide what happens, in this order: don't merge them, they have different answers and different sources:

**First: is this project even an agentics adopter?** This is a property of the *project*, not of you. Don't gate it purely on finding a well-formed pin: an early adopter may carry none, and a project missing it entirely is exactly the case that most needs to be caught, not silently skipped. Treat a project as an agentics adopter if *either* is true: an `agentics-template-version` tag in any form, or (failing that) `AGENTS.md`/`CLAUDE.md` merely mentions agentics (`grep -qi agentics AGENTS.md CLAUDE.md 2>/dev/null`), e.g. the "Adapted from softeng/agentics" line the template ships with: prose survives trimming better than an HTML comment. If neither is present, this isn't (detectably) an agentics project: nothing to check, though see `conventions/upgrading-adoption.md` § 0 for the case where a project shares the lineage with no textual trace at all.

**Second, only if the answer above is yes: how strongly do you personally need to check?** This is a property of *you, the agent* (specifically, your global context), not of the project: a project mentioning agentics doesn't by itself make the check mandatory; your own contributor status does. Two tiers, deliberately different in strength:

- **Opt-in, for any adopter** (`propagation_suggestions: yes`, resolved the same way as the outbound question in `convention-levels.md` § Propagation suggestions: global default, locally overridable per project): check for this at session start alongside the outbound question, same treatment as any other project.
- **Mandatory, for agentics contributors** (`agentics_contributor: yes`): record this in your global context, not only in agentics' own project memory: it needs to apply in every project you work in, not just sessions inside agentics itself. For a contributor, this check runs every session in every project, regardless of that project's own `propagation_suggestions` setting, and keeps recurring for an unresolved gap rather than surfacing it once and going quiet if it's ignored or deferred. This is intentionally more insistent than the opt-in tier: contributing to agentics implies a higher bar of keeping the ecosystem you're helping build actually current, and a prompt that quietly stops repeating itself is easy to forget about. Run this same pass in the reverse direction too: see `convention-levels.md` § Propagation suggestions, "Proactive, not just reactive."

**This has to be phrased as an unconditional override, not just a mandatory flag, or it silently loses to a project's own checklist.** A project with a complete, self-contained "Starting a session" list, the exact legacy pattern in `upgrading-adoption.md` § 1, will win against a global instruction that only says "do this check every session," because the agent reasonably treats the project's own explicit, complete instructions as sufficient and never separately reasons "is there something the global context wants me to do in addition to this." Tested directly: a global instruction phrased as a plain recurring step failed against that pattern; the same instruction, rephrased to explicitly say the check runs *in addition to* the project's own checklist even when that checklist is complete and its own dispatch-to-global line names other topics but not this one, succeeded. State the override explicitly in your global context: name the failure mode (a complete local checklist, a narrower dispatch line) and say directly that neither one opts a project out: only `agentics_upstream_check: no` does.

The mandatory tier stops only on an explicit instruction from the user, at one of two scopes: never inferred from silence or a deferred "not now":
- **"Stop for this project":** record `agentics_upstream_check: no` in that project's own memory. Suppresses the check there only.
- **"Stop for all projects":** record `agentics_upstream_check: no` in your global context instead. Suppresses it everywhere, without touching the other agentics-contributor behaviours (outbound propagation, named in the section above, stays always-on): this is a separate flag, not a downgrade of `agentics_contributor` itself.

**Noticing staleness is the start of this procedure, not a substitute for it.** Reading a pin and recognizing "this project is behind" is not the same as having actually run the steps below: an agent did exactly the first half, read enough to know a project's version tag was several releases old, then moved on to unrelated work without ever fetching the diff, reading the new entries, or running the diagnosis, treating the notice itself as if it were the completed check. Detecting staleness obligates running the rest of this procedure in the same sitting, not deferring it implicitly by moving on to other work; if it's genuinely being deferred, say so explicitly and let the user decide, the same "not a soft offer the user can wave off with no trace" standard the no-pin case already holds.

**A copied `AGENTS.md`**, one holding its own § When to read what rather than pinning a release, predates release tags. Its tag, with or without a `synced:` commit, names the release matched by its copy, and its agent reads conventions from the newest commit. Compare that version as steps 1 and 2 do, then run `upgrading-adoption.md`, whose one-time migration replaces the copy with a pin.

**A pin present** (the normal, steady-state case):

**Locating agentics' own repo isn't the same as checking this project's pin, don't conflate the two.** Especially relevant in a shared multi-root workspace where agentics itself sits as a sibling directory alongside the project you're actually checking: it's easy to read agentics' own current `CHANGELOG.md`/`HEAD` state and answer "what version am I on" from that, instead of from this project's own pin, `<!-- agentics-template-version: X.Y.Z -->`. A session determined it was "running agentics 0.14.0" by reading agentics' own `CHANGELOG.md`, while the actual project it was working in had a stamped tag reading a much older version, several releases behind, including the release that introduced the very rule it then missed. The two facts answer different questions: agentics' own current version is a fact about the upstream template; this project's pin is the only fact that says what this project actually reads.

1. With no agentics entry in your global context, ask the user for the address of an agentics repository they can open and record it, per agentics' `template/conventions/initialization.md` § Recording where agentics lives. Then locate the local agentics clone if the entry records a `Path`. Don't just prefer it by default: verify it's actually current first, and verify the right thing. `git -C <agentics-path> remote -v` and confirm one of the configured remotes actually matches the agentics entry's `Repo URL`. Without this check, comparing against whatever `@{u}` happens to resolve to can't tell "0 commits behind" (true) from "0 commits behind a stale or unintended fork this clone happens to track" (false reassurance). If the entry's `Repo URL` isn't among the configured remotes at all, don't trust this clone for freshness purposes: fall back to the remote URL and say so. If it is: `git -C <agentics-path> fetch` and compare local `HEAD` against that remote's branch specifically. If local is behind, use the same fallback, and tell the user the clone is behind: bringing it current is separate work, per **If it's your own local agentics clone that's stale** later in this file. A verified-current local clone beats a live remote read. A stale or wrongly-sourced one is worse than the URL, not better, since it can report "nothing changed" when the opposite is true.
2. Read agentics' `CHANGELOG.md` at its newest commit, from the verified clone or from the `Repo URL` at `main`, as agentics' `template/AGENTS.md` § When to read what describes, from its `## Released` heading down to the pin's own `### X.Y.Z` heading, skipping `## Unreleased changes`, whose entries never reach a pinned project, never the whole file. The command in § Security notices for every pinned project reads exactly that range. Each `### X.Y.Z` heading above the pin's is a release newer than the pin. If there is none, nothing changed: stop here, no further context spent. A pin matching no heading is a typo or an invented version: say so, and treat the project as having no pin. A pin of `main` follows the newest commit by choice, so no release is newer: name the newest release once per session, so the user can pin it when done trying unreleased conventions, and stop.
3. Don't stop at printing the entries. Run the diagnosis in `conventions/upgrading-adoption.md` § 1 against the newest release, for real: a changelog entry is a pointer to what to look for, not a substitute for re-deriving what the project's copied files need (is `CLAUDE.md` still a stub? does the project's § Critical constraints match that release's?). This is what closes the gap between "the changelog mentioned it" and "the project's files actually reflect it": a structural fix described in prose is easy to read past without translating into an action, and re-running the diagnosis does that translation instead of leaving it to the user.
4. Check `.dev/agentics-overrides.md` if it exists; suppress any gap that matches a recorded permanent decision there rather than resurfacing it.
5. Classify and batch what's left exactly as `upgrading-adoption.md` § 2 describes (non-conflicting fixes batched behind one confirmation, conflicts asked about individually with the three-way choice); don't re-derive the classification here, that section is the one place it's defined. Lead with any `breaking: yes` entries in either bucket: their **Migration:** step usually names a copied file, not just a referenced one, and the step has to be applied, not just acknowledged. Also check whether any new entry formalizes something already tracked informally in this project's own memory (a workaround noted as a habit, a fact recorded as project-specific): if the new convention now covers it, prune or trim that memory entry too, rather than leaving both copies to drift apart. This is a different check from whether a new entry contradicts, rather than formalizes, something already tracked: a duplicate restates a fact already in memory and gets pruned once the convention covers it, but a contradiction means the new convention now says something different from what the memory recorded as settled, and needs surfacing to the user as a real conflict, not silently resolved either way.
6. Once reviewed (applied, explicitly skipped, or recorded as a permanent override), move the pin to the newest release, last, per `upgrading-adoption.md` § 2. Moving it is what brings the newer rules in, so a pin moved with a migration step unapplied leaves the project reading rules its copied files do not match.
7. Having moved the pin, announce it, because you are the only party who knows it happened. If `agent_index: yes` is in your global context, post one sync notice naming the repository on the Requests board (`conventions/agent-index.md` § Requests carries the shape and the supersession rule), replacing any previous notice for that repository. Where you already hold an address for a session working in the same project, send it directly as well: the board is durable but unread until someone opens it, and a direct message is what actually reaches a session that is mid-task.

**Moving the pin makes every concurrently running session in that project stale, and takes away the signal that would tell them.** Each of them read `template/AGENTS.md` at the old pin. Their check, if they ran it, was correct when it ran. A session that never stopped does not run it again. And the pin they would re-read now matches the current one, so the evidence that they are behind is identical to the evidence that they are current. This is the reason step 7 exists rather than being a courtesy: the failure is silent on their side and only visible on yours.

**The obligation on the other side is self-detection, and it does not depend on anyone reaching you.** The pin is not just a thing you check, it is a value you hold. If you read it at session start and read it again later and it has moved, a peer moved it underneath you, and the rules at the new pin are ones you have never read. Re-read `template/AGENTS.md` at the new pin at that point, with the entries between the two releases. Do this at the checkpoints that already exist, the pre-commit re-check in particular, rather than on a timer.

**Notification is the accelerant and self-detection is the mechanism, never the reverse.** Cross-session messaging is capability-gated and may not exist for a given agent at all, so a rule that depends on being told fails silently exactly where nothing else covers it. The two also fail under opposite conditions, which is why both are here: self-detection breaks when long-thread context loss takes the earlier value with it, and that is precisely the long-running session most likely to be carrying replaced conventions.

**Each tagged copy in your global context needs this check separately, under the same two tiers as a project's check.** `personal-preferences.md`, `AGENTS.softeng.md`, `AGENTS.overture.md` and any `AGENTS.roles/<role>.md` are snapshots taken at different times, so they drift independently, and comparing only the one you remember is how another goes unnoticed. Run steps 1 to 5 against each, comparing its version as step 2 compares a pin and ignoring any SHA beside it, then re-copy it at the newest release's tag and restamp it with that release's version and no SHA. A project's own check never substitutes for this one. Security entries are the exception to these steps: § Security notices for every pinned project reports them for each copy, and its remedy re-copies only the copies named by an entry, with no full check.

**A project's pin being ahead of your own global tag is backwards, and worth fixing immediately, not just noting.** Global should generally lead or match every project, never trail one: refreshing your own global tag is cheap and personal, no team coordination needed, unlike a project update. If a project's pin names a later release than your own global tag, that's a sign your global context missed an update a project session already picked up; bring your global tag current in the same sitting you notice this, not deferred as a stale local clone (below) can be.

**If it's your own local agentics clone that's stale, not the project you're checking:** a different axis from the numbered steps above, and relevant only to agentics contributors (`agentics_contributor: yes`). An opt-in `propagation_suggestions` adopter doesn't necessarily keep a local agentics clone at all, so this doesn't apply to them. Flag it plainly, once, in whatever session happens to surface it, then don't switch into fixing it there: pulling, re-pointing a remote, or otherwise repairing your own agentics clone is real, separate work, and derailing a session that was never about agentics maintenance to go do it is its own kind of gap. Instead, record a reminder in your own global context or memory, not this project's files: this is about your personal environment, not project content. Offer to fix it next time that's actually convenient. Same reasoning as a deferred tech-debt item: note it once, let it wait, don't force it into whatever's happening right now.

**Unreleased entries never reach a pinned project.** `CHANGELOG.md` accumulates entries under `## Unreleased changes` for long stretches, and they wait for a release, or for a pin of `main`.

**No pin:** don't run step 2: there's no baseline to compare from, and a full historical walk back to adoption is mostly agentics' own internal iteration, not necessarily relevant to this project. Instead, run the full procedure in `conventions/upgrading-adoption.md` § 1 directly: it surfaces the entries of the release it pins as a bounded first-encounter catch-up and covers the pin, session-file migration, and `AGENTS.md` completeness together, rather than patching the pin in isolation. This isn't a soft offer to wave off without a trace: a project with no pin at all is exactly the case most likely to carry real, unreconciled structural drift, since nothing has ever diagnosed it against the template. Treat it the same as a newer release in step 2: same `.dev/agentics-overrides.md` check first, same classification into a batched non-conflicting proposal and individually-asked conflicts.

## Security notices for every pinned project

**At session start, every project whose `AGENTS.md` pins a release checks for security entries, whatever its `propagation_suggestions` answer.** The version tag of a copied `AGENTS.md` counts as a pin here. A pin of `main` already reads the newest commit, so it skips this check.

**Outside a pinned project, the global context runs the same check against its own version tags alone**, per `personal-preferences.md` § Security notices, so a fix to a global copy reaches a user who works without an adopted project. Inside a pinned project, `session-discipline.md` step 6 already covers the global tags, so the check runs once.

1. Take `X.Y.Z` as the oldest of the project's pin and the version tags in your global context. Pipe agentics' `CHANGELOG.md` at its newest commit, read as agentics' `template/AGENTS.md` § When to read what says (`curl -fsS <raw address> |` or `git -C <Path> show HEAD:CHANGELOG.md |`), into this command, which prints every entry under `## Released` above the heading for `X.Y.Z`, dated or not, and stops there. It prints `unknown pin` and nothing else when no heading matches, and next to nothing when the project is current:

   ```
   awk -v v='X.Y.Z' 'BEGIN { gsub(/\./, "[.]", v); re = "^### " v "( |$)" }
     /^## Released/ { on = 1; next }
     on && $0 ~ re { found = 1; exit }
     on { buf = buf $0 "\n" }
     END { printf "%s", found ? buf : "unknown pin\n" }'
   ```
2. An entry whose category is `security`, as in `date | security | bump | breaking? | slug`, concerns this project when its release is newer than the pin. It concerns a global copy, `personal-preferences.md`, a role or team file, or `security-guidelines.md`, only when the entry names that copy and its release is newer than the copy's own version tag. `security-guidelines.md` carries no tag, so it is dated by the tag on `personal-preferences.md`.
3. Report one notice per entry: its release, its slug, and everything it concerns. Offer the remedy for each: for this project, the upgrade in `upgrading-adoption.md`; for a global copy, re-copying that copy alone at the newest release's tag and restamping its version tag with that release, with no full check first. An entry concerning nothing gets no notice.

If the read fails, the failure rule in the project's `AGENTS.md` covers it; with no project, tell the user once and go on.
