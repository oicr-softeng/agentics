# Upgrading a project's agentics adoption

Moving a project's pin to a newer agentics release, and bringing its copied files to match that release. Three ways in:

- **The user asks directly:** "upgrade this project's agentics integration," "update your agentics," "sync agentics," or any similar phrasing built around "update" or "sync" plus "agentics." Read "update" here as "fetch the latest agentics content and apply what's relevant to this project," never as "edit the agentics source itself," the same disambiguation agentics' root `AGENTS.md` § Critical constraints already states for the reverse case, a session arriving at agentics' own repo from elsewhere. A bare "update" reads equally plausibly as "update the thing I have" (the upstream source) or "update how this project uses it" (this procedure) until disambiguated. Run this procedure now, unconditionally: even if this session already believes the project is current, an explicit ask means verify it for real against the actual repo, not skip ahead on the assumption that an earlier check, by this session or a different concurrent one, already settled it.
- **The automatic session-start check finds something stale or missing** (see `upstream-check.md`): this procedure *is* what that check runs, not something it merely offers. It fires whenever a release newer than the project's pin exists, or the project has no pin or still holds a copied `AGENTS.md`, gated by the same tiering already described there (mandatory for `agentics_contributor: yes`, opt-in via `propagation_suggestions: yes` elsewhere). A security notice is the ungated route: `upstream-check.md` § Security notices for every pinned project offers this procedure in every pinned project, whatever the user opted into.
- **Agentics running this against itself** (agentics' root `AGENTS.md` § Repo maintenance rules, "adopter zero"): the "project" and the "upstream template" are two files in the same repo, not two repos. § 0's detection answers "yes" immediately. In § 1, skip the clone-vs-URL lookup, since `template/` is already sitting right there, and skip the version-tag and copied-`AGENTS.md` bullets, since this repo's own `AGENTS.md` carries no pin and is agentics' own file rather than a copy.

Nothing in this procedure auto-commits or applies without the user seeing the proposal first. Give the user a plain-language summary of each change, with the diff available on request, and let them approve it (batched where nothing conflicts, individually where something does, see § 2). Once it is applied, offer to commit and push it, since every technical step is yours.

**An upgrade is moving the pin.** A pinned project's agent reads `template/AGENTS.md` and every convention at the pin, so what an upgrade changes in the project is the pin itself, the copy of § Critical constraints, any other copied file named by a breaking entry's **Migration:** step, such as `CLAUDE.md` or `.claude/settings.json`, and the user's global context where an entry says so. The target release is the newest under `CHANGELOG.md` § Released unless the user names another. Read this procedure, and every file it names, at the target release rather than at the current pin, as agentics' `template/AGENTS.md` § When to read what says, since a release can change how a project upgrades to it.

## 0. Confirm this project is actually meant to track agentics

Detection, in order:
1. `AGENTS.md` or `CLAUDE.md` carries an `agentics-template-version` tag, in any form.
2. Failing that, either file mentions "agentics" at all (a bare `grep -qi agentics AGENTS.md CLAUDE.md`), e.g. the "Adapted from softeng/agentics" line the template ships with.
3. Neither is present. Don't assume either way: ask the user directly. Some projects converge on the same conventions independently without ever referencing agentics: a real, tracked case (see `CHANGELOG.md` § `upgrading-adoption`). If the user confirms this project should be tracked, ask where that fact should live:
   - **In this project's own files:** add a tag or a short mention to `CLAUDE.md`/`AGENTS.md`, same as a formal adoption. Straightforward, but it's one more file to remember.
   - **In the user's `~/.claude/projects.md`** (or equivalent global registry), as an explicit "track this project against agentics" marker, without touching the project's own files at all. Lower friction if the user manages many such projects, since it's one registry instead of N repos to remember.
   
   Don't default to one silently: this determines what step 1 below checks against, and it's the kind of thing that's ugly to walk back if guessed wrong.

## 1. Diagnose gaps against the current template

**Diff the files, do not hand-map the changelog.** Compare this project's copied files against the target release directly, its `AGENTS.md` against `template/AGENTS.project.md` and its § Critical constraints against `template/AGENTS.md`'s, and let the diff tell you what is missing. Reconstructing the same answer by reading changelog entries and inferring which file each one touched is slower, and it fails silently: a dense entry describing a rule can easily not name the file it landed in, so an entry read correctly still yields nothing. The diff is exact, needs no interpretation, and does not care how many releases accumulated. The diff is exact and mechanical, so run it inline rather than through subagents, where a second opinion changes nothing (`session-discipline.md` § Starting a session).

**When drift spans several releases, rewrite the file rather than patching it.** Incremental edits against a file that has fallen behind by multiple releases get error-prone fast, since each patch lands in a context the next one assumes differently. Rewriting from the canonical template, then re-adding this project's own legitimate local content, is more reliable and easier to check. The cleanest sync audited so far used both.

**Reading a convention during the sync is itself a check on this project.** A file you pull in because the dispatch table changed often states requirements the project has never been measured against. Applying `entry-formats.md`'s required `fix:` field this way caught the same real formatting gap in two repos, and reading it prompted a check of one project's own recorded claim that new tests used a particular runner, which turned out false against its actual suite: fifty-four specs, none of them using it. Both fixes came from reading a convention rather than from looking for problems.


Read the target release's files at its release tag `vX.Y.Z`. Check each of the following, current vs. desired, and report the diagnosis **before changing anything**: a short list of what's stale, so the user isn't surprised by the size of the change:

- **Local overrides:** read `.dev/agentics-overrides.md` if it exists (format in § 2). Any gap found below that matches a recorded permanent decision there is already resolved: don't re-report it, don't re-ask about it.
- **Version tag:** a pin naming a release, or the tag of a copied `AGENTS.md`? Read the entries between its version and the target release as `upstream-check.md` step 2 does, ignoring any `synced:` commit beside it, and lead with `breaking: yes` entries, since each **Migration:** step among them is part of this upgrade. A pin of `main` has no release behind it: ask whether to pin the target release now. With no tag at all, there's no baseline to compare from, so don't attempt one. Instead, surface the target release's entries as a bounded, one-time catch-up: deliberately not a full historical walk back to this project's original adoption date (mostly agentics' own internal iteration, not necessarily relevant here), but also not nothing, since pinning silently without showing anything would swallow whatever migration steps that release carries. Lead with any `breaking: yes` entries, same per-entry consent as the normal flow.
- **A copied `AGENTS.md`:** one holding its own § Interaction parameters or § When to read what, rather than a pin and a pointer to agentics, predates release tags. It needs the one-time migration in § 2, whatever its tag says.
- **The credential hook, checked by behaviour rather than by diff, and before anything else on this list:** run the self-test in agentics' `docs/security-for-developers.md` against the project's `.claude/settings.json`, and against the user's global settings file too if the hook is installed there, which `template/README.md` explicitly allows. **Any `allow` in the output is a security defect, not a pass**: a PreToolUse hook returning `allow` skips the permission prompt, so a guard that allows every path it does not block switches off the default prompts for every tool it does not cover. Versions of the template before 0.21.0 shipped exactly that, and the file is copied at adoption rather than read live, so no convention change reaches it; this check is the only thing that does. Behaviour rather than a text diff, because adopters routinely add their own patterns and a diff would report every customization as a gap. Surface a failure ahead of every other finding, including the `breaking: yes` catch-up, since a batch can carry dozens of those and a security fix among them is easy to scroll past.
- **Global-context-scoped entries:** while reading new entries (from either path above), some describe a fix to the *reading agent's own global context*, a flag that should be recorded globally instead of per-project, a stop-mechanism, anything scoped to "your settings" rather than a file copied into this project. These won't show up as a gap in any of the project-file checks below: nothing here diffs the agent's own persistent config against anything. Read new entries for this category specifically; don't assume every entry means "check a file in this project."
- **Does `CLAUDE.md` itself have a complete, self-contained "Starting a session" (or equivalent) checklist that predates agentics?** If so, check whether its own dispatch-to-global line (often under a "Workflow" heading) names specific topics deferred to global context. If "session discipline" isn't on that list, the project's session behavior isn't deferring to agentics at all, however well the global context is set up elsewhere: a well-tuned global dispatch cannot override a project's own explicit, narrower instructions, and shouldn't try to. This is most likely why an automatic upstream-update check never fires on an old project: not a bug in the check, a genuinely un-migrated file. This case needs the same treatment as thin/absent `AGENTS.md` content below, applied to `CLAUDE.md` too.
- **Session files:** `.dev/sessions.md` (single shared file) vs `.dev/sessions/` (one file per contributor per day)? The old model needs the migration in step 2.
- **AGENTS.md completeness:** does it match `template/AGENTS.project.md` at the target release, apart from the pin and the project's own sections, with § Critical constraints word for word as in `template/AGENTS.md`? Or does it point at the user's global context instead, or hold nothing at all? A version that only works from someone's personal global-context setup silently fails for any contributor who doesn't share it. This isn't hypothetical: it's exactly why an update can look "done" to one contributor and be invisible to a teammate reading the same repo. Prefer the pin and the pointer to agentics over a pointer to a contributor-specific setup.
- **Bootstrap artifacts missing locally (`conventions/`, `AGENTS.roles/`, `AGENTS.softeng.md`, `AGENTS.overture.md`) are never a gap to fix in the project**, regardless of whether the user's global context currently covers the equivalent content: see `convention-levels.md` § How much to keep locally for the full rule. Never include creating any of them in the non-conflicting batch below, don't ask about them as a conflict either, and don't propose them as an upgrade fix under any circumstance.
- **Agent-neutrality:** does anything copied in reference `~/.claude/...` or "Claude Code" unconditionally, with no `(for Claude: X; for other agents: Y)` framing? Run `grep -rn '~/\.claude\|Claude Code'` over the copied files, leaving out `CLAUDE.md`, whose whole purpose is Claude Code.
- **Do `CLAUDE.md` and `AGENTS.md` actually agree with each other?** They're meant to cover the same ground, but drift independently since each gets edited on its own schedule: a project can end up with, say, a six-step "Starting a session" checklist in one and a four-step version in the other. Diff the two files' checklists directly rather than only comparing each one to the template; a project can look "upgraded" from one file's perspective and be behind from the other's.
- **`.dev/roadmap.md` and `.dev/tech-debt.md` content itself, not just their format:** scan existing entries, not just check the files exist in the right shape, for personal names or individual attribution (`AGENTS.md` § Critical constraints ("Name code, not people")), process or event narrative in place of the concrete decision or issue an entry should state (`session-discipline.md` § Keeping `.dev/` current), and any instructional comment restating the tech-debt format already defined in `entry-formats.md` § Tech-debt entry format rather than referencing it. None of these are hypothetical: a live adopter had all three at once.
- **New initialization questions added since this project's initial setup:** `conventions/initialization.md` only runs "if no project memory exists yet," so a question introduced after a project already has memory never gets asked, project memory simply has no recorded answer to something that didn't exist when it was set up. Check each current question in `conventions/initialization.md` against project memory and the global context; anything unanswered needs asking now rather than waiting for a fresh-init scenario that won't recur. Current live instance: "Overture project?" (see `AGENTS.overture.md`).
- **`.github/copilot-instructions.md` specifically: check whether it's still needed at all before checking whether it's in sync.** GitHub Copilot's coding agent, its CLI, and VS Code's Copilot Chat (enabled by default) all read `AGENTS.md` directly; a separate file is no longer required for Copilot to pick up this project's conventions. If one exists as a full, independently-maintained copy rather than a stub, that's now pure duplication risk with no offsetting benefit, propose retiring it (or reducing it to a stub) rather than keeping it in sync, the treatment given to any redundant agent-specific file by the design principles in agentics' root `CONTRIBUTING.md`. A real project's copy had already drifted, missing an entire session-start step (the agentics upstream-check) and several security-trigger details gained by `AGENTS.md` since.
- **Other agent-specific instruction files** (a Cursor rules file, or similar, not covered by the Copilot case above): if the project's own documentation says to keep them in sync with `CLAUDE.md`/`AGENTS.md` (check `DEVELOPMENT.md` or an equivalent contributor guide), give it the same treatment: at minimum the session-file mechanics, since those are agent-neutral and apply regardless of which file a given tool actually reads.

## 2. Apply, with consent per change

Classify each gap from § 1 before proposing anything:

- **Non-conflicting:** a pure addition (the current template has a section, rule, or file the project doesn't have at all), or a mechanical structural fix where the local copy is just a stale, unmodified instance of an older template shape, nothing local was ever deliberately changed to diverge from it. Batch every non-conflicting gap into one proposed diff and ask once: a single yes/no covers the whole batch.
- **Conflicting:** local content is a deliberate, substantive customization that diverges from the current template's current handling of the same topic (e.g. a project that intentionally kept an abridged version of a section). **A local divergence that breaks a rule the template states is a defect, not a customization**, so it is fixed with the non-conflicting batch and never offered as an override: a tech-debt entry kept with a "Fixed." note, where `session-discipline.md` says to remove addressed entries, is one. A divergence is conflicting only when its reason survives the current rules. Ask about each of these individually, never batched, with three choices:
  1. **Adopt upstream:** replace the local version with the current template's.
  2. **Keep local, just this time:** leave it as-is; it stays a gap and will be asked about again next time this check runs.
  3. **Keep local, permanently:** leave it as-is and record it in `.dev/agentics-overrides.md` (format and general purpose in `convention-levels.md` § Recording a permanent override; this procedure is one trigger for it, not the only one) so it stops being flagged. § 1 reads this file before reporting a diagnosis and drops anything already listed here.

- **Migrating `.dev/sessions.md`:** split by date. For multi-contributor history, split by date only: don't try to retroactively attribute old entries to individuals; past conflicts are already resolved. The `(day, contributor)` filename scheme (`YYYY-MM-DDTHHMMSS.md`, no slug) only needs to apply going forward. See `session-discipline.md` § Session file identity for the exact rules. This is a cutover, not an addition: once every entry has a home in `.dev/sessions/`, delete `.dev/sessions.md`. Copying content out while leaving the source in place isn't a completed migration, it's a duplicate that reintroduces the exact shared-file merge-conflict risk targeted by the new format. Don't leave a placeholder file (e.g. `.gitkeep`) in `.dev/sessions/` once it holds real content: it existed only to make an empty directory trackable, and is noise once files exist there.
- **Asking any new initialization question found unanswered in § 1:** non-conflicting (there's nothing local to override, just a question with no recorded answer yet); ask it in the same batch pass rather than treating it as its own special case. Record the answer in project memory (or global context, if that's where the question says it belongs) the same as during initial setup.
- **Fixing `.dev/roadmap.md`/`.dev/tech-debt.md` content found in § 1:** scrub a name to a generic description, trim process narrative down to the concrete decision or issue, remove a duplicated format-instruction comment (pointing at `entry-formats.md` by name if a reference is actually wanted). These are non-conflicting: there's no legitimate reason to keep an individual's name, a restated format comment, or event narrative in place of the decision it should state, so batch them with the other non-conflicting fixes rather than asking about each individually.
- **Moving the pin, last:** set the first line of `AGENTS.md` to `<!-- agentics-template-version: X.Y.Z -->`, the target release, once every other change in the batch is applied, since the pin decides what the next session reads. Take `X.Y.Z` from the first `### X.Y.Z` heading under `CHANGELOG.md` § Released, never from a partial log or from where `## Unreleased changes` begins, which tells you what has not shipped rather than what has. Drop any `synced:` commit beside the version: the pin carries none. Then read `template/AGENTS.md` at the new pin once. Where that read fails and a read at `main` succeeds, the release has no release tag: keep the old pin and tell the user.
- **Re-syncing the copies, verbatim:** replace the project's § Critical constraints with `template/AGENTS.md`'s at the target release, word for word, and do the same for any other copied file, `CLAUDE.md` included, only where a migration step names it. For Claude, `.claude/settings.json` is merged rather than replaced, keeping patterns the project added, and the credential-hook check in § 1 confirms the result. **Copy upstream wording exactly rather than restating it in your own words.** Paraphrase drops qualifying clauses, and it does so invisibly, since the result reads fine and only a diff against upstream reveals what went missing. The one exception is content where this project deliberately diverges, recorded in `.dev/agentics-overrides.md`: there the local wording wins and the upstream version is not applied at all, which is a different case from paraphrasing it. § Critical constraints never takes that exception: a project's tightening goes in its own constraints section, and the copy stays verbatim. If `CLAUDE.md` still keeps its own copy of the dispatch table instead of pointing at `AGENTS.md`, fix that too: one table, not two kept in sync by hand.
- **Migrating from a copied `AGENTS.md`, once.** A project adopted before releases were tagged holds a full copy of `template/AGENTS.md`, under a tag naming the release matched by the copy and often a `synced:` commit, and its agent reads conventions from the newest commit. Replace it with the pointer file as one change, summarized to the user whole before anything is written, since no upgrade changes an instruction file more:
  1. Find the project's own content. With a clone, diff the copy against `template/AGENTS.md` at the release named by its tag, found with `git -C <Path> log -1 --format=%H --grep '^Release X.Y.Z:'`, and what remains is the project's. Without one, diff against `template/AGENTS.md` at the target release, and ask about each line that is neither in the template nor plainly the project's own.
  2. Copy `template/AGENTS.project.md` at the target release over the file, and set the pin per the bullet on moving the pin.
  3. Carry the project's own content into the places labelled for it: constraints, extension points, repository structure, and any other section of its own. A wording that differs from the template's is carried, into the project's constraints, only where `.dev/agentics-overrides.md` records it as a deliberate divergence; otherwise it is an older template wording, and the pinned release replaces it.
  4. Replace `CLAUDE.md` with `template/CLAUDE.md` at the target release.

- **Applying a global-context-scoped fix** (see § 1): this isn't a file in this project. Check the agent's own global context for the setting the entry describes, correct it if it's missing or recorded in the wrong place (e.g. per-project instead of global), and confirm the correction actually happened before treating the finding as resolved. Reading the entry's text and moving on is not applying it: a described fix that was only narrated, not checked and corrected, is exactly the gap targeted by this step. A global copy re-copied this way, such as `personal-preferences.md` or a role file, is read at the target release's tag, and its version tag is restamped with that release, so its security notices clear.
- Every change here is still a change to an instruction file (or the equivalent for session logs), or a correction to the agent's own global context: the user sees a plain-language summary of each proposed change before anything is written, with the diff on request, batched or not, and a global-context correction gets confirmed the same way, not just narrated. What changes is how many separate decisions that takes, not whether a decision happens at all.

## 2b. Sweep backwards for what the change invalidates

**A convention change names a rule, not a point in time.** Applying it only to new work leaves the existing corpus asserting whatever the old rule allowed, and a reader cannot tell which entries predate the change. So when a change makes some class of content not worth keeping, the existing files are the unswept instance set, and finding them is part of applying the change rather than a separate tidying project. Same shape as `definition-of-done.md` § A report names an instance, along a different axis. **This sweep is the part of an upgrade that earns a fan-out**, since every match has to be read; keep it off the critical path of anything urgent.

**Sweep mechanically and report by file and category**, not from a memory of where such content might be. A grep for the newly forbidden pattern, counted per file, is the proposal's evidence.

**Immutability yields to this, and the reason is narrow.** `entry-formats.md` makes a session file immutable once its day closes, which protects a record from casual revision. It was never meant to preserve content that should not have been written, and a frozen file asserting what the conventions now forbid is worse than an edited one, because nothing can correct it and its readers have no way to know. So a closed session file is in scope, and that is the one case where the immutability rule is deliberately set aside rather than argued around.

**A pattern count is the size of the search, not the size of the problem, and the gap is usually an order of magnitude.** Measured on the first real run of this procedure: a grep for newly-forbidden patterns returned 86 occurrences across 17 files, and reading every line reduced it to one genuine fix in two files. Acting on the count would have been mostly destructive, and would have looked thorough. So the count opens the investigation and never authorizes the edit: **read every matched line before proposing anything.** If that is too many lines to read, the proposal is too large to make in one pass, not a reason to skip the reading.

**Classify each match before choosing what to do with it, because removal is one of four operations and usually not the right one.** Sorting those matches gave four categories, and each takes a different action:

- **A genuine defect**, asserting something the new rule forbids: remove it, or rewrite it to say only what survives.
- **The project's own subject matter.** A convention about a mechanism will discuss that mechanism, and a project defining the rule is the one place where the "violation" is the content. Leave it.
- **True but environment-specific**, asserted as though universal: the defect is the missing scope rather than the content, so **disclose it** with a header naming the environment. See `documentation.md` § An environment-specific finding.
- **Already disclosed.** Someone marked it at the time, e.g. "(outside this repo)". Leave it, and notice that the existing marking is the pattern worth spreading.

**Where a dead identifier is carrying evidence, generalize rather than delete.** An empirical finding often names the instance that produced it, and the identifier goes stale while the finding stays true. Replacing "session `arranger-56` showed no observable effect" with "a long-running session in another workspace showed no observable effect" keeps the claim and drops the dead value; deleting the sentence removes the basis for something true, which is the falsification boundary below running in the other direction.

**Never silently, and the explanation is the deliverable.** Bring the user what you propose to remove, from which files, and why the new rule invalidates it. A diff with no reasoning is not a proposal, because the user cannot check the judgment that produced it. Let them choose the granularity: file by file for anything contentious, or one approval for a batch that is clearly uniform. Some of what a sweep surfaces will be legitimate on inspection, so expect the answer to be partial rather than yes or no.

**Removing what misleads is cleanup; rewriting to appear compliant is falsification, and the line is not subtle.** Delete a line that asserts machine-local state as project fact. Do not rewrite a past entry so the file reads as though the new convention was always followed, add reasoning absent at the time, or adjust a recorded decision to match current thinking. **The test: after the edit, does the file claim anything untrue about what happened?** If yes, that is not a sweep, and the honest form is removal plus a note in the current session's file that a past entry was pruned and why.

## 3. Record it

Log the upgrade in this project's own session file (create `.dev/sessions/` now if this run is what introduces it), listing the pin moved from and to, each copied file compared against the target release, each migration step applied, and anything newly written to `.dev/agentics-overrides.md` this run. **The list is the only record of what this upgrade checked**: an upgrade that compared only § Critical constraints still moves the pin, and without the list the next one cannot tell what this one skipped. Then offer to commit and push it, so other contributors pick up the change on their next pull: not automatically, and not until then.

This procedure reads a lot: multiple files, diffs, CHANGELOG history, back-and-forth diagnosis. None of that has ongoing value once the migration is applied, and it stays in context adding token weight to whatever comes next in the same thread. If your harness gives you no way to reset or clear your own context window, recommend the user start a fresh chat or session for subsequent work rather than continuing in this one: the same "new thread is cheaper than accumulating" reasoning already in `session-discipline.md` § Starting a session, just more pronounced here given how much this specific procedure tends to read.
