# Agent collaboration template

This directory contains template files for setting up AI agent collaboration. `AGENTS.project.md` is copied into your project root as `AGENTS.md`, where it pins an agentics release, and `CLAUDE.md`, `DEVELOPMENT.md` and, for Claude, `.claude/settings.json` are copied in too (see § How to adopt). `AGENTS.md` and `conventions/` are read live from agentics at that release. `AGENTS.roles/`, `AGENTS.softeng.md`, `AGENTS.overture.md` and `global-context/` are global-guideline material, read live from agentics or used once to bootstrap your agent's own global context. No file in either group belongs copied into a project.

## How to adopt

Copy every file below as it stands at the release you pin, its release tag `vX.Y.Z`, so the copies match what your agent reads.

1. Copy `AGENTS.project.md` to your project root as `AGENTS.md`, replace its first line with the pin as § Keeping up to date says, and fill in its places for this project's own rules; also copy `CLAUDE.md` if you use Claude Code (it auto-loads that file specifically, but stays a stub pointing at `AGENTS.md`)
2. Copy `DEVELOPMENT.md` and fill in your project-specific setup steps, unless the setup answer `role` is `general` or the project already has its own setup guide
3. Create a `.dev/` directory with `roadmap.md`, `tech-debt.md`, and a `sessions/` directory holding the session file that records the adoption. `roadmap.md` starts as a `# Roadmap` heading over one line naming the current focus, or `No focus set yet.` where there is none. `tech-debt.md` starts as a `# Tech debt` heading with no entries, each later one in the format of `conventions/entry-formats.md` § Tech-debt entry format. A further file, `agentics-overrides.md`, is created on demand when the user first permanently declines a convention's recommendation for this project (see `conventions/convention-levels.md` § Recording a permanent override): don't create it empty upfront
4. Add `.claude/memory/` and `.claude/settings.local.json` to this project's `.gitignore`. `.claude/settings.local.json` holds machine-specific paths and usernames and belongs on one machine only, and agentics' `template/AGENTS.md` § Memory and contribution hygiene says why a memory directory there should never exist. An older adoption or another agent may have created either one, and untracked is not the same as ignored: `git add -A` commits it. This is containment, separate from the rule that prevents it.
5. For Claude: copy `.claude/settings.json` to enforce the credential file blocklist, or skip it if your global `~/.claude/settings.json` already has the hook. The hook runs `python3`, so where `python3` is missing, skip it and say so, since it would fail on every tool call. Once the hook is copied, the agent runs the self-test in agentics' `docs/security-for-developers.md` § Verify the credential blocklist yourself against it, with the test script saved outside the project, such as in a temporary directory, and treats any `allow` in the output as a defect to fix before going on. For other agents: nothing equivalent ships, so build the block in your tool's own permission or deny-list system (agentics' `docs/security-for-developers.md` § Know what the blocklist does not cover)
6. If your agent's global context doesn't yet define your role, your team's conventions (e.g. softeng), or your product family's (e.g. Overture), bootstrap it once from the role file named for your `role` in the answer table of `conventions/initialization.md` § Setting up a project, `AGENTS.softeng.md`, and/or `AGENTS.overture.md`: each is appended to your global context file with its own version tag at the top of the appended block, as `global-context/README.md` § Bootstrapping without a project says. This is a one-time action on your global context, not a per-project step

**`conventions/`, `AGENTS.roles/`, `AGENTS.softeng.md`, and `AGENTS.overture.md` are global-guideline material: they never belong copied into a project, under any circumstance.** See `conventions/convention-levels.md` § How much to keep locally for the full rule and why. The project's `AGENTS.md` holds only what `AGENTS.project.md` carries plus project-specific content: constraints, extension points, and repo structure notes.

## Keeping up to date

**The first line of your project's `AGENTS.md` is its pin: `<!-- agentics-template-version: X.Y.Z -->`**, set at adoption to the newest release under agentics' `CHANGELOG.md` § Released. Each release commit carries the git tag `vX.Y.Z`, and your agent reads this directory's `AGENTS.md` and every convention at that tag, so a later release changes nothing in your project until you move the pin. Inside agentics the line carries a pointer instead, `<!-- agentics-template-version: see CHANGELOG.md § Released (latest entry) -->`, which resolves to nothing once copied. A pin of `main` follows the newest commit, for trying conventions not yet released. `CLAUDE.md` carries no pin: it's a stub pointing at `AGENTS.md`.

To upgrade, ask your agent to upgrade the project's agentics adoption. It reads the changelog entries between your pin and the newest release, applies the **Migration:** step of each one marked breaking once you approve it, re-copies § Critical constraints from this directory's `AGENTS.md` at the new release, and moves the pin, per `conventions/upgrading-adoption.md`. If you opted in to propagation suggestions at initialization, recorded as `propagation_suggestions: yes` in your global context, your agent checks for a newer release at session start (see `conventions/upstream-check.md`). Whatever you answered, your agent tells you at session start of any newer release that fixes a security weakness. Without that opt-in, ask your agent now and then whether agentics has a release newer than your pin; it reads the [agentics CHANGELOG](../CHANGELOG.md) to answer. A project adopted before releases were tagged holds a full copy of `AGENTS.md` instead, and the same procedure replaces it once with `AGENTS.project.md`.

## Already have an existing setup?

If you already have a `CLAUDE.md`, `AGENTS.md`, or other agent instruction file, don't replace it: merge instead. Add what `AGENTS.project.md` carries, from the pin to § Critical constraints, to your existing agent-neutral file (or create `AGENTS.md` if you don't have one), and keep your existing rules as the project's own, which win over agentics' on conflict, except that none may loosen a critical constraint. The conventions stay in agentics, read at the pin, regardless of what your existing setup already covers. Softeng conventions are designed to supplement existing practices, not override them, and belong in your global context, not this project, same as any other adoption.

## Security

Agentics ships agent-facing security conventions, but part of the posture is yours and cannot be automated. Read [`docs/security-for-developers.md`](../docs/security-for-developers.md) in the agentics repo yourself, once: it covers what to verify yourself, which of your agent's claims about its own work are unreliable, and the trust boundaries only you can hold. If you copied `.claude/settings.json`, it also gives you a short command to confirm the credential blocklist is actually live rather than silently allowing everything.

## Contributing back

If you establish a convention or improve a practice in your project that could benefit other teams, consider opening a PR to the agentics repository you adopted from. Your agent can help identify candidates: agentics' `template/AGENTS.md` § Memory and contribution hygiene includes a reminder to check when writing to project memory.
