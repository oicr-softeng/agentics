# Contributing to softeng/agentics

For contributors to agentics, people and their agents: how to propose a change, version and release it, and add a role file. This repo distributes the devctx collaboration template, the `AGENTS.md`, `.dev/` and convention files adopted by a project or by a developer's own global agent configuration. Changes here propagate to teams and users who adopt it: design with care.

## Design principles

- **Dispatch over inline**: `AGENTS.md` stays lean; convention detail lives in separate files loaded on demand. Full reasoning: `README.md` § Two tiers
- **Agent-neutral**: template files must not assume one agent tool, in a path, a mechanism or a term (for Claude: `~/.claude/` or "compaction"; for other agents: their own equivalents); use the general form, such as "your agent's global context directory", with a `(for Claude: X; for other agents: Y)` parenthetical where the specific detail is needed
- **`AGENTS.md` is the single source; other agent-specific files are stubs, not copies, or not needed at all:** `CLAUDE.md` (root and `template/`) holds no conventions of its own, only a pointer to `AGENTS.md`, because Claude Code loads it automatically and something has to exist for that purpose. GitHub Copilot needs even less: its coding agent, CLI, and VS Code's Copilot Chat (enabled by default) all read `AGENTS.md` directly, no `.github/copilot-instructions.md` required at all, not even a stub, see the `.github/copilot-instructions.md` bullet in `template/conventions/upgrading-adoption.md` § 1 for what to do about a project that already has one. If this repo ever adds guidance for another agent-specific file that genuinely needs its own (a Cursor rules file, say), give it the stub treatment: pointing at `AGENTS.md`, never a second copy of content. Independent copies drift: when both files carried content, they diverged repeatedly, in a missing section, a missing bullet and a version-tag rule naming only one file's tag (`CHANGELOG.md` § `agents-md-single-dispatch-table`). If you're ever tempted to add real content to `CLAUDE.md` beyond a pointer, that's the regression to watch for
- **No credentials**: see `AGENTS.md` § Critical constraints, the authoritative statement
- **No personal identifying details**: see `AGENTS.md` § Critical constraints for the rule itself. Everything committed here, `.dev/sessions/` included, is read by people with no context for who you are or what machine you use. A personal GitHub username and a contributor's first name have both reached committed docs here
- **Additive, not prescriptive**: role and org files add or modify the base; they do not replace it
- **Lean project files**: a downstream project's `AGENTS.md` is a copy of `template/AGENTS.project.md`: a pin naming a release, a copy of § Critical constraints and project-specific content, with everything else read from this repository at the pin. `CLAUDE.md` stays a minimal stub pointing at `AGENTS.md`; it exists only because Claude Code loads it automatically, not as a second place to hold content
- **Explicit audience**: don't rely on filename or folder structure alone to signal that a file is agent instructions rather than human documentation: a person unfamiliar with the convention won't necessarily infer it. `CLAUDE.md`/`AGENTS.md` (both root and template) say so explicitly in their opening lines; a file that's genuinely dual-audience (e.g. `docs/agent-security.md`) says that instead. Apply the same to any new agent-facing file whose purpose isn't obvious from context
- **Adopt agentics, not pieces of it**: write about adoption at the level of "adopted agentics" (fully or partially), not "adopted a convention from agentics." The latter frames agentics as a menu to pick items from rather than a system to bring in; whether a given convention ends up copied locally or left as a live pointer is an implementation detail underneath that, not the framing itself
- **Convention entries: rule and edge-case reasoning inline, incident narrative in `CHANGELOG.md` only**: a convention file entry should read as the rule, then just enough reasoning to let an agent judge a case not explicitly enumerated by the rule. It should not re-narrate the specific incident that produced it: which adopter, what they typed, what broke, exact quotes. That story already exists exactly once, in the corresponding `CHANGELOG.md` entry; a convention file re-telling it is a second copy that can drift from the first. Cross-reference by slug (`see CHANGELOG.md § <slug>`) instead of duplicating it. This keeps convention files terse for the audience that reads them every session or on demand, without losing the story anywhere. Caution: some reasoning currently embedded in a convention *is* the instruction, not decoration (e.g. `definition-of-done.md` § Verifying conformance, not just structure explains a non-obvious *why now*, not just *why*), don't sever those mechanically; judge each case
- **Succinct wording is a separate pass from non-duplication.** Removing an incident narrative (the principle on convention entries) doesn't by itself make the remaining rule read tightly: the rule-plus-reasoning that's left can still be padded, restating the same point twice in different words. Same discipline as `template/conventions/writing-style.md` § Say it once (canonical), applied here to convention prose specifically
- **A rule is only as good as the moment it is read at: place it where its reader arrives, not where it belongs by topic.** The recurring failure in this repo is not missing rules, it is correct rules filed by subject matter in a file never opened at that moment by the person who needs them. Five instances, each on a different surface: a threat model dispatched only on a trigger that never coincides with the exposure it describes; two human-facing security documents linked from neither README; three debugging lessons filed under code-writing and PR-review, where a session whose whole task is "this is broken" loads neither; a session-log rule stated in `documentation.md`, which nobody opens while writing a session log; and completion criteria dispatched on a trigger that fires after the work is done. When adding a rule, name the event that should invoke it, then check that the reader has already opened the file carrying it by then. If it is not, either move it or add a dispatch line: a cross-reference from a file they are not reading does not count. This is the same reasoning behind "the reference has to be an instruction, not a citation" in `convention-levels.md`, applied to placement rather than phrasing.
- **Write the rule around what actually varies, not one example of it.** A convention phrased as "alphabetize config files" or "don't hardcode `~/.claude/` paths" reads, to the next reader, as scoped to exactly that: config files, paths. The example was meant to illustrate a broader property (any list of named entries; anything that differs by which tool is running), but nothing in the wording says so, so the next person or agent applying the rule has no reason to go further than what's literally written. Fix this by naming what the rule actually depends on, with the concrete case following as an example, not standing in for the rule's real scope. This has happened often enough in this repo to check for it deliberately, not treat each case as a one-off: `code-style.md` § Property ordering needed widening from config files to code to markdown documents before it named "named entries" as the real scope; "agent-neutral" needed the same correction applied to a session-continuity mechanism, not just paths. See `CHANGELOG.md` from `property-ordering-covers-code` onward for the specific incidents

## Agent setup for contributors

**Contributors work from a local clone, which no one else needs.** Record its path as `Path` in the agentics entry of your global context's cross-project map (`template/conventions/initialization.md` § Recording where agentics lives), so your agent reads conventions from your clone, including changes you have not pushed. For Claude, a `Read(~/path/to/agentics/**)` rule under `permissions.allow` in `~/.claude/settings.json` lets sessions in every project read the clone without asking, while edits to it still go through your permission prompts; write `//` in place of `~/` for a clone outside your home directory.

If you use an AI agent and are actively contributing to agentics, set the following in your **global context**, the configuration your agent loads in every project (for Claude: `~/.claude/`; for other agents: see your agent's documentation), not just this repo's project memory, since it needs to apply in every project you work in, not only sessions inside agentics itself:

```
agentics_contributor: yes
```

This enables three behaviours without needing to opt in per session or per project:
- Propagation suggestions are always on: your agent surfaces convention improvements proactively
- The agentics repo is always named as an explicit candidate, alongside the project and global levels
- The upstream-update check becomes mandatory, not opt-in, in every project you work in, regardless of that project's own `propagation_suggestions` setting, and keeps recurring every session for an unresolved gap rather than surfacing it once and going quiet. This is deliberately more insistent than the standard opt-in tier: contributing to agentics implies keeping the ecosystem you're helping build actually current is part of the job. It stops only on an explicit "stop for this project" (recorded in that project's memory) or "stop for all projects" (recorded in your global context), never inferred from silence: someone who'd rather turn this off entirely than deal with it is signalling something about how invested they actually are in contributing, which is fine, but it's their call to make explicitly.

If your role is developer or AI engineer, your agent asks about this on your first session in this repo (root `AGENTS.md` § Initialization), and should record the answer in your global context, not (only) this repo's project memory. You can also set it manually in your global context at any time.

See `template/conventions/upstream-check.md` for what this looks like in practice.

## Proposing changes

1. Identify which level the change belongs at: see `template/conventions/convention-levels.md`
2. Make the change and add a CHANGELOG entry under `## Unreleased changes`. A change sharpens an existing section by default, and earns a new one only for a class not covered by any section: see `template/conventions/documentation.md` § Cross-linking, not duplication
3. If you added a new `conventions/*.md` file, it needs to be reachable from two places, not just created: a dispatch line in `template/AGENTS.md`'s "When to read what" table (the single canonical dispatch list; `template/CLAUDE.md` points at it rather than keeping its own copy), and a row in `template/README.md`'s file table. A file that's real and useful but missing from either is invisible to whoever needed it: this happened to `security.md`, leaving its pnpm guidance unreachable, and to `documentation.md` and `upgrading-adoption.md`
4. See § Versioning below for the `bump` field and the CHANGELOG-as-source-of-truth rule
5. Mark `breaking: yes` in the CHANGELOG if a project moving its pin past the change, or a copy in a user's global context, needs a manual update, and state that update as the entry's **Migration:** step
6. If the change touches the dispatch table (`AGENTS.md`'s "When to read what"), or a procedure whose output gets copied verbatim into another project (`upgrading-adoption.md`, `initialization.md`), dry-run it against a fixture before considering it done, not a real project: see `testing/fixtures.md`. A change that reads correctly in the abstract, or passes plan-mode discussion, can still fail once actually applied; design approval is not execution verification. `testing/README.md` indexes this and the other verification practices (`testing/` is contributor-only, never copied into an adopting project). A change to `template/AGENTS.md` § Critical constraints goes into `template/AGENTS.project.md` word for word, and is breaking, since every project re-copies it; `testing/scripts/check-consistency.sh` fails while the two differ. If the change is specifically to `template/AGENTS.md` or `template/CLAUDE.md`, also run the self-check in `AGENTS.md` § Repo maintenance rules ("adopter zero"): reconcile this repo's own `AGENTS.md`/`CLAUDE.md` against the new template version before considering the change done. **This step is not optional because the change looks small, was already discussed in the same conversation, or was already reviewed once**: none of those are a substitute for actually running it, the same override needed by `agentics_contributor`'s mandatory tier once it turned out "do this every session" alone lost to a project's own checklist (`CHANGELOG.md` § `contributor-check-explicit-override`). The incidents behind this step started from confidence that a change was fine
7. Run once per clone, not per commit: `git config core.hooksPath .githooks`. This wires `testing/scripts/check-consistency.sh` into a pre-commit hook (`.githooks/pre-commit`) that blocks the commit on failure. The script is the authoritative list of what it checks; `testing/consistency-checks.md` gives the reasoning behind the original checks and what still needs your own judgment (it surfaces candidates, it doesn't clear them). Mechanical checks shouldn't depend on anyone remembering to run them; see `docs/deterministic-by-design.md`
8. **If this formalizes something you were tracking informally in your own personal or project memory, prune or trim that memory now, not at a later audit.** As a contributor, you're the one creating the staleness, in the same breath you fix the underlying gap, unlike an ordinary adopter, whose memory only goes stale when they happen to sync a new template version. The right check point is immediately after shipping the convention, not an occasional separate pass: leaving it for later is exactly how redundant memory accumulates unnoticed. Point the memory at the new convention if anything in it is still worth keeping (an anecdote, an origin story the convention itself doesn't capture); remove it entirely if the convention now fully covers what the memory said

## Versioning

Semver, with major reserved: agentics stays at `0.y.z` until productization is explicitly authorized; major only moves once that's decided.

**`CHANGELOG.md` is the only place a version number lives.** Under `## Released`, each dated entry (`### 0.2.0 - 2026-07-15`) is a past version; the first one is the current one. Nothing else stamps a copy of this number. **A template file carries a version tag only when a copy of it is read outside agentics in place of the original and `template/conventions/upstream-check.md` compares that copy's tag.** Add the tag and that comparison together. A file never copied out, or one deployed as the user's own data, carries none. Inside this repo a tag is a pointer, `agentics-template-version: see CHANGELOG.md § Released (latest entry)`, stamped with a version on copy: see `template/README.md` § Keeping up to date. `testing/scripts/check-consistency.sh` holds the list of tagged files and fails a tag on any other.

**Every CHANGELOG entry carries a `bump` field**: `date | category | bump | breaking? | description`. **An entry fixing a security weakness in a convention, the credential hook or a check takes the category `security`**, as in `date | security | bump | breaking? | slug`, since every project pinned to an older release is told of it at session start, whatever it opted into (`template/conventions/upstream-check.md` § Security notices for every pinned project). Write it as what the code must do, never how an earlier version failed, per `template/conventions/security.md` § Releasing the fix for a hole carried by a published release.
- `bump: patch`: fixes, clarifies, backfills, or propagates something already intended elsewhere in agentics. Nothing new is introduced.
- `bump: minor`: introduces a rule, file, procedure, or section that didn't exist in any form before.
- If a change feels major-sized (a true incompatible restructuring, not just "adopters need to re-sync"), flag it explicitly when logging it rather than silently tagging it `minor` and let the user decide how it's recorded.

`breaking: yes/no` stays a separate, orthogonal signal (does an adopter need to take action), not the semver driver. Entries under `### 0.1.0` predate the field and carry none.

**Rollup**: the next version, when you actually want to know it, is `## Released`'s current top entry bumped by the *highest* `bump` level found across everything currently under `## Unreleased changes`. Multiple `minor` entries since the last release still only bump minor once, not once per entry. This is computed on demand, not maintained as a running value anywhere: `CHANGELOG.md` already holds everything needed to derive it, so there's nothing to keep in sync by carrying a second copy of the answer.

**Publishing a release**: triggered by an explicit request, phrased directly ("publish this", "release this", "cut a release", "ship it") or indirectly ("let's have this published", "let's let others propagate this"), the explicit-plus-indirect pattern used for a different trigger by `template/conventions/session-discipline.md` § Session-start signals; don't wait for one exact phrase. On trigger: first, the staleness pass called for at session start by `session-discipline.md` § Keeping `.dev/` current (mark completed roadmap items done, remove addressed tech-debt entries), applied here as a precommit step rather than only a session-start one, since a release commit is exactly the kind of checkpoint where `.dev/` drifting from reality would otherwise go unnoticed until the next session happens to catch it.

**If the release fixes a hole carried by an earlier release, it follows `template/conventions/security.md` § Releasing the fix for a hole carried by a published release before anything is pushed.** Two of its steps fall to the user and cannot be done by an agent: closing the hole on every installation run by the team, and drafting the security advisory in the repository's Security tab, published together with the release. Agentics is copied rather than installed, so no package tooling will notify an adopter. The advisory, and the session-start notice of the release's `security` entries, are the only notices that reach one who does not read the changelog.

Then a simplification pass: read what's about to ship against the current state of the files it touches and ask whether anything can be simplified, de-duplicated, or replaced with a pointer to something that already exists elsewhere, rather than a new part restating it. This is a standing check at every release, not the one-time retroactive trim done under `terse-conventions-cite-changelog`, and per `AGENTS.md` § Repo maintenance rules it isn't gated on this trigger either: this occurrence is a backstop, most of the batch, everything under `## Unreleased changes`, should already have been through it at earlier natural completion points in the session. Run the matching scenario in `testing/regression-checklist.md` afterward if the simplification touches a section with a regression entry, to confirm it didn't silently remove the behaviour supported by the removed words. Before moving anything under a dated heading: check each `## Unreleased changes` entry against `testing/regression-checklist.md`'s own stated criteria (a fix to how an agent interpreted an instruction, not a pure content addition) and add a matching entry now for anything that qualifies and doesn't already have one. This is a forced step at every release, because the reminder in that file's header alone let several qualifying fixes go unrecorded for two releases running, the fragile-memory pattern targeted by `docs/deterministic-by-design.md`. **Sweep cross-references by hand if any section moved between files during the batch.** Relocating a section leaves every pointer that named its old home dangling, and each individual move looks correct at the time, so this only appears in the aggregate: 0.19.0's relocation of sections between convention files broke pointers that way, four of which outlived the hand sweep run at the time (`CHANGELOG.md` § `four-more-pointers-broke-in-the-0-19-0-move`). `testing/scripts/check-consistency.sh` checks positional pointers, flagging a section or phrase named with "above" or "below" that is not on that side in the same file. A named reference into another file is not checked, because headings here contain backticked paths, carry numbered prefixes and run on into prose, and every matcher tried traded one false positive for another. For those, grep the moved section titles across `template/`, `docs/`, and the root files. Also before finalizing: do a brief unprompted gap-scan of what's about to ship, not a full audit, just whether this batch reveals an adjacent problem worth surfacing now (a wording pattern that recurred, a file that should have been touched but wasn't, a decision left dangling). Same standing discipline as "surface ideas... unprompted" (`AGENTS.md` § Interaction parameters), applied here as a fixed checkpoint rather than left to fire only when directly asked. Then confirm the rollup bump (see **Rollup** in this section), then move the `## Unreleased changes` entries under a new dated `### X.Y.Z - <date>` heading inside `## Released`. The date in that heading is the day the release is committed, not the date of any entry inside it: entries already carry their own dates, a release just gathers entries logged across however many days into one dated event. Nothing else needs touching, since no other file holds the number.

**Tag the release commit, because a project pinned to the release reads agentics at the tag.** Once the release commit exists, the agent adds an annotated tag on it, `git tag -a vX.Y.Z -m "Release X.Y.Z"`, and the user pushes the tag with the release to every remote that publishes it, `git push <remote> main vX.Y.Z`. An amend after tagging leaves the tag on the replaced commit, so move it with `git tag -fa` before the push. Never move or delete a pushed tag, since every project pinned to it reads through it. A release without a tag cannot be pinned, and releases before this step existed carry none.

**The simplification pass has a gate, because a sentence alone did not make it run.** `scripts/check-prune-ratio.sh` measures the net change in characters across files under `template/` and `docs/` against `origin/main`, new files included, and fails a batch whose net growth exceeds its budget. It deliberately measures the fact rather than the judgement: what to cut needs a person or an agent, while how much the batch grew is arithmetic. **The hook is `.githooks/commit-msg`, beside the existing `pre-commit`, so the `core.hooksPath` setting in § Proposing changes already covers it and there is nothing extra to enable.** It is contributor-only and never reaches adopters, since `.githooks/` is not part of `template/`. It fires the pruning gate on a `Release X.Y.Z` subject and rejects AI-tool attribution on every commit. Both rules sit in a hook rather than a script, since a script that depends on being remembered is inside the failure it exists to fix, and a hook is not. A hook can still be bypassed, which is the point rather than a weakness: it converts forgetting into deciding. `testing/scripts/check-consistency.sh` reports the same verdict advisorily during ordinary work, where failing the loop would only train skipping.

**`main` carries release commits only, which is this repo's own publishing rule.** `template/conventions/git.md` states the general one: iteration on a unit of work collapses, separate units stay separate. agentics collapses further, because it publishes releases rather than commits and `main` is the artifact, so everything between two releases becomes one commit. Amend the single unpushed commit as work continues rather than adding to it. The reasoning is the same as for session files: a series of commits arriving at a final state documents the path rather than the outcome, and here nobody can bisect, review in stages, or revert one piece independently, so the intermediate states carry nothing. **This is agentics-specific and does not travel with the template.** An adopting project keeps separate commits for separate units of work.

**Narrow commit exception**: publishing a release is the one explicit exception to this repo's otherwise-general "never commit" rule, and it applies to any agentics contributor, not just this repo's lead developer. Scoped tightly: only inside this specific ritual, only after the publish trigger has actually fired. The agent commits the release (the batch with its `CHANGELOG.md` relocation, as the one commit since the last release, with no work from outside the batch) and tags that commit; the user pushes both themselves. This does not authorize committing anything else, staging anything else, tagging any other commit, or committing without the trigger.

**Commit message**: subject follows the established release pattern, `Release X.Y.Z: <headline change>`, where `X.Y.Z` is the version just moved under `## Released` and the suffix is a declarative one-line summary of the release's most significant change. The version is included here because only in release commits does git history intentionally mirror the released changelog heading, for scannability; `CHANGELOG.md` remains the canonical source for the value everywhere else. Body is a verb-first list of the rest of what actually changed in substance, adds X, removes Y, improves Z, not how the release was assembled: don't describe relocating `CHANGELOG.md` entries or confirming the rollup, that's process, not content, and skip relative day words ("today," "earlier"), which mean nothing once committed. There's no build or compile step here: `main` is the artifact, so a commit is effectively already live the moment it lands; the message doubles as the release notes.

## Creating a new role file

Role files live in `template/AGENTS.roles/`. Each one describes what to add, modify, or de-emphasize relative to the base template for a specific type of user.

### Steps

1. Create `template/AGENTS.roles/<role>.md` using this structure:

   ```markdown
   <!-- agentics-template-version: see CHANGELOG.md § Released (latest entry) -->
   # <Role name>

   [Who this is: 1-2 sentences, plain language, no jargon]

   [Optionally: Builds on: AGENTS.roles/general.md: read that first.]

   ## [Relevant section]
   [What the base template adds or changes for this role]

   ## De-emphasize from base template
   [Conventions less relevant to this role, and why]
   ```

2. Add the role name to the role question in `template/conventions/initialization.md`, which `template/AGENTS.md` dispatches to, and the role's key value and file to the answer table there. The same list of roles also appears in `README.md` § Quick start, root `AGENTS.md` § Initialization and `template/global-context/README.md`

3. Add a CHANGELOG entry:
   ```
   date | template | minor | no | role-<name>: add AGENTS.roles/<name>.md: <one-line description>
   ```

### What goes in a role file

- Communication style (plain language vs. technical, jargon threshold)
- Domain-specific conventions (data pipelines for bio, prompt hygiene for ai-eng)
- Session discipline adaptations (how `.dev/` files translate for non-technical users)
- Security additions specific to the domain
- What to de-emphasize from the base

### What stays out of role files

- Credentials, secrets, private URLs: never, in any file
- Org-specific content: goes in the org layer (e.g., `AGENTS.softeng.md`)
- Project-specific content: goes in the project's own `AGENTS.md`
- Anything only one agent tool has, whether a path, a mechanism or a term (for Claude: `~/.claude/`; for other agents: their own equivalents): role files are agent-neutral

### The `general` role as foundation

`general.md` is for users who may not work with files, code, or software projects at all. It is the foundation for non-developer specialist profiles. If you are creating a role for a non-developer audience (admin, ops, clinical, legal), start from it:

```
Builds on: AGENTS.roles/general.md: read that first.
```

Then add only what is specific to that audience.
